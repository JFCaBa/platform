# Load more departures (up to ~4 h ahead)

Goal: when the user scrolls to the end of the list (or taps "Show more"), add the next trains, up
to about 4 hours ahead. Same feature as Andén (tren repo, commits 1407686 and 3c96160), but here
the data comes from Darwin through our API, so each extra page is a network request.

## Constraints

- Darwin GetDepartureBoard: `timeOffset` -120..119 min, `timeWindow` up to 120 min, `numRows` (we
  use 50). So the furthest reach is offset 119 + 120 min window ≈ 4 h.
- At busy stations 50 rows cover less than 2 h (e.g. ~40 min), so pages must follow the last
  train shown, not jump to fixed 2 h blocks (that would leave gaps).
- Darwin calls should stay low: no fair-usage cap, but a ~100 req/s spike arrest (429) and the
  poller for /follow shares the key.
- Privacy and URL rules stay as they are: nginx rebuilds the upstream URL from captured parts;
  the cache key is built from those parts only.

## API (api/platform_api/server.py, deploy/nginx/whatplatform.uk.conf)

1. New route `GET /departures/{CRS}/{OFFSET}`, OFFSET an integer 1..119 without leading zeros
   (anything else → 400). `/departures/{CRS}` is unchanged (offset 0, 50 rows) and keeps serving
   /follow and the poller.
   Darwin query for extra pages: `?numRows=150&timeWindow=120&timeOffset=OFFSET` (150 = Darwin's
   maximum: even at the busiest stations a page then covers well over 15 min, and offset 119
   reaches further).
2. Response = same board shape plus two fields, also added to the offset-0 board:
   - `timeOffset`: the offset asked for (0 for the base board).
   - `complete`: true when fewer rows than asked came back (the whole 120-min window is covered).
3. Same slot pool as the base board (`slots`), same error mapping (429/404/502).
4. nginx: new `location ~ "^/departures/([A-Z]{3})/([1-9][0-9]?|1[01][0-9])$"`, then
   `set $crs $1; set $off $2;` as elsewhere in the file, upstream URL rebuilt from them,
   `proxy_cache_key "$crs:$off"`. Cache 200 for **60 s** (pages are snapshots of later trains;
   the base board stays at 30 s). Same lock/stale rules. gzip on for application/json.
   The app asks for multiples of 15 (plus 119), so every user of a station shares the same few
   cache entries; an exact minute is only used in the saturated case below.
5. Tests (api/tests/test_server.py): valid offsets reach Darwin with the right timeOffset and
   numRows=150, invalid ones (0, 120, 07, -5, abc) are 400, `timeOffset`/`complete` are in the
   body, the base board is unchanged apart from the two new fields.

## App (app/lib)

1. `DeparturesClient.fetch(crs, {int offset = 0})` → `/departures/CRS` or `/departures/CRS/OFFSET`.
   `Board` gains `timeOffset` (default 0) and `complete` (default false when missing, so an older
   API never claims to be complete; the app then just asks for the next page).
2. `AppController` keeps, per station, the base board (as now) plus a list of extra pages
   (snapshots, each with its fetch time). Reset on station change and on pull-to-refresh.
   - Shown list = union of base + pages, deduplicated by serviceId (fallback std+destination),
     the most recently fetched copy wins (so the base, refreshed every 30 s, replaces a page's
     copy once it reaches it), sorted by absolute departure time: std "HH:MM" turned into a
     London date-time relative to the fetch time, so trains after midnight sort after 23:59.
     Page trains scheduled before the base's first train are dropped (they have left; a delayed
     one is still in the base). `visibleServices`/`destinations`/filters work on this list.
   - `hasMore` = last loaded offset < 119 (independent of the base's `complete`).
   - Next offset, from the last train in the shown list: m = minutes from now (London) to its
     std. If the last page was `complete`: previous offset + 120, capped to 119. Else
     q = floor(m / 15) * 15 capped to 119; if q > previous offset use q, else (a saturated page
     covering < 15 min) use m itself (exact minute, overlapping, no gap), capped to 119; if
     that is still <= previous offset, stop (`hasMore` false).
   - `loadMore()`: one request at a time (ignored while one is in flight); a spinner at the end
     of the list while loading; a failure keeps what is shown and the button stays to retry;
     429 uses the existing rate-limit backoff.
   - Darwin calls: the 30 s refresh fetches only the base board, as now. Extra pages are never
     refreshed on their own; their etd/platform can be a few minutes old (2–4 h ahead they
     rarely change) until the base reaches them or the user pulls to refresh. No disk cache.
   - Filters do not reset the pages (unlike Andén, pages are network data worth keeping); a
     filter just narrows the list. "Show more" stays while `hasMore`.
3. UI (home_screen.dart): ScrollController with the same rule as Andén (within 300 px of the
   end → loadMore, one per frame), plus a "Show more" TextButton at the end while `hasMore`,
   replaced by a spinner while loading. When `hasMore` is false and the list is non-empty:
   a small note: "No more departures in the next 4 hours" if the last page was `complete`,
   else "That's as far ahead as we can show".
4. Tests (app/test): client builds the offset URL; controller merge/dedupe (newest copy wins,
   same-minute trains kept, departed page trains dropped), next-offset rule (busy station,
   saturated page → exact minute, complete page, midnight wrap, cap at 119, stop), one request in
   flight, pages not refetched by the 30 s refresh, reset on station change and pull-to-refresh; widget test for button + scroll.

## Rollout

1. API first: tests, deploy (git pull, docker compose up -d --build, copy nginx conf, nginx -t,
   reload). The base board change is additive, so the shipped apps are unaffected.
2. Then app; ships in 1.2.0 (8) build, which is still waiting for 1.1.0 approval.
3. Update docs/platform/darwin-notes.md (timeOffset use) and docs/store/estado.md.
